# 54% · 行为测量（现场 + 报告）

作品的完整形态有两段：

| 段落 | 载体 | 作用 |
| --- | --- | --- |
| **现场** | `index.html` 摄像头实时 | 让观众看到一个煞有介事的百分比在跳动 |
| **拆解** | 页面内按钮 → 三套方案并排 | 同一份数据的结论从 32% 到 96%，当场推翻自己 |
| **总结** | 页面内「生成总结」 | 整段会话的统计 + 事件时间轴 + 六种口径并排 + 可导出报告 |
| **离线视频** | 页面内「分析视频」 | 选一个视频文件，本地逐帧测量，自动出同一份总结 |
| **报告** | `run.py`（Python 离线管线） | 对一段真实访谈出完整分析报告 |

离线管线把视频拆成可核对的行为事件，并**如实展示这类判定的不稳定性**。

四个分析器：

| 分析器 | 产出 | 通道 |
| --- | --- | --- |
| **OpenFace** | AU 强度、头部姿态、视线 | `face` / `head` |
| **DeepFace** | 7 类离散情绪 | `emotion` |
| **Whisper** | 带词级时间戳的转写 + 语速 | `asr` / `word` / `prosody` |
| **MediaPipe** | 姿态、肩线倾角、头肩偏移 | `pose` |

## 快速开始

### 1 · 浏览器实时端（现场演示用这个）

```bash
cd face-54
python -m http.server 5174
# 打开 http://127.0.0.1:5174/
```

必须走 HTTP（`file://` 下 ES Module 会被拦），摄像头也要求 localhost 或 https。

界面是五面板布局：

| 面板 | 内容 |
| --- | --- |
| 实时画面 | 摄像头 + 478 点三角网格（含鼻子）+ 轮廓线 |
| 动作单元活动 | 最近 20 秒、5 条通道的实时波形 |
| 通道数值 | 8 个信号的当前值 + 强度条 |
| 事件日志 | 时间 / 动作 / 强度 / 时长，超过阈值的动作自动记录 |
| 底栏 | 行为指标 + 三套方案对比 + 声明 |

工具栏：开始采集 / 演示数据 / **分析视频** / 停止 / **生成总结** / 清空。

现场如果摄像头出问题，点「演示数据」切成合成信号继续演示——逻辑完全一样，只是数据是生成的。

## 分析总结（会话结束后）

停止采集（或视频分析完成）后点「生成总结」，得到的是一份完整的测量记录：

| 区块 | 内容 |
| --- | --- |
| 指标 | 采集时长、人脸检出率、事件总数、微表情占比、事件频率、口径跨度 |
| 事件时间轴 | 每类动作一行，事件按时间落点，微表情用高亮条区分 |
| **六种口径** | 三套方案 × {全程平均, 动作峰值}，最低/最高单独标出 |
| 动作分布 | 次数、次/分、均强度、均时长、微表情数、占比 |
| 替代解释 | 出现最多的三类动作，各自列出 4–5 种同样合理的解释 |

六个数字排成一行是本作品的核心：**同一段事件序列，最高 98.9%「高度提示存在隐瞒」、最低 40.9%「倾向于未隐瞒」，
中间还夹着「无法判断」**。差别只在于用哪套假设加权、取全程平均还是动作峰值。

三种导出：

| 按钮 | 产物 |
| --- | --- |
| 保存 HTML 报告 | 自包含 HTML（内联样式 + SVG 时间轴），双击即开，可直接打印或发送 |
| 保存时间轴 PNG | 2400px 宽位图，用于做图、贴进幻灯片 |
| 导出事件 CSV | 带 BOM，Excel 直接打开不乱码，含替代解释列 |

> **没有事件时不会摆出六格 50.0%。** 那是「没有输入」，不是「无法判断」的测量结论——
> 这两种情况被刻意区分开，空状态会明确写「数据不足，无法给出任何读数」。

## 分析视频文件（浏览器端）

点「分析视频」选一个本地文件，全程在本机完成，不上传：

- 2 倍速播放，逐帧送给 FaceLandmarker 测量
- 时间基准取 `video.currentTime` 而不是墙钟——2 倍速下两者差一倍，用墙钟会让所有事件时长和刻度整体错位
- 预览面板实时显示进度，分析完成后自动打开总结
- 只支持浏览器能解码的格式（mp4 / webm），失败会给出具体原因

### 2 · 离线报告

不需要装任何重型依赖，先用合成数据看整条链路和报告长什么样：

```bash
python run.py --demo -o demo-report.html --json
```

输出 `demo-report.html`（报告）和 `demo-report.json`（原始数据）。

### 调试参数

| 参数 | 作用 |
| --- | --- |
| `?demo=1` | 直接进演示模式，跳过启动页 |
| `?explain=1` | 自动展开拆解层 |
| `?still=1` | 关闭所有过渡（无头截图用） |
| `?dbg=1` | 把实时指标写进页面标题 |
| `?fake=60` | 伪造一段 60 秒会话并直接打开总结面板（无头截图验证用） |
| `?vidurl=/x.webm` | 直接分析指定地址的视频，自检离线链路 |

> 无头浏览器里 `performance.now()` 不随虚拟时间加速，动画只能跑约 0.9 秒，
> 所以你截图看到的实时数值接近基线。这不是 bug——事件检测与打分逻辑已在 Node 里单独验证过。

## 分析真实视频

```bash
python run.py interview.mp4 -o report.html --json
```

**每个分析器都是可选的**：装了就跑，没装就跳过，不会中断管线。报告的技术附录会列出每个分析器的状态。

### 安装

```bash
pip install -r requirements.txt
```

**Python 版本**：建议 **3.10 – 3.12**。3.13 上 `mediapipe` 和 `tensorflow`（DeepFace 依赖）的 wheel 还不完整，会装不上。

**OpenFace** 不在 pip 里，需要单独下载：

```bash
# 下载预编译版后，指向可执行文件
set OPENFACE_BIN=C:\OpenFace\FeatureExtraction.exe     # Windows
export OPENFACE_BIN=/opt/OpenFace/build/bin/FeatureExtraction   # Linux/macOS
```

不设置 `OPENFACE_BIN` 也可以，只要 `FeatureExtraction` 在 PATH 里。

### 只跑部分通道

```bash
python run.py interview.mp4 --only openface,whisper -o report.html
```

## 这个管线真正难的地方：时间对齐

四个工具各有各的时钟，直接拼起来会出现「00:32 皱眉的同时语气变紧」这种错位 1–2 秒的假阳性。

`pipeline/timeline.py` 做两件事：

1. **用 ffprobe 读流信息**，拿到视频流和音频流的真实 `start_time`，算出 `audio_offset`
2. **全部归一到「视频起点 = 0」** 的同一根时间轴上

```python
class MediaClock:
    audio_offset = audio_start - video_start

    def audio_to_video(self, t):     # Whisper 的秒数 → 视频时间轴
        return t + self.audio_offset

    def frame_to_video(self, n):     # OpenFace 的帧号 → 视频时间轴
        return n / self.fps
```

音频和视频的起点经常不一致（ffmpeg 合并、编码延迟、容器封装）。跳过这一步，后续所有交叉分析都不可信。

另外 `runs_above()` 负责从连续信号里提取事件区间（微表情只持续 1/25–1/5 秒，约 2–6 帧，阈值必须压到 0.06 秒量级），并会补上短暂空洞，避免一个事件被拆成几段。

## 为什么报告不给「是否说谎」的结论

`pipeline/fusion.py` 里放了四套方案：

| 方案 | 假设 |
| --- | --- |
| A · 常见说法 | 压抑情绪会泄漏：皱眉、抿嘴、视线躲闪 = 隐瞒 |
| B · 同样合理 | 紧张的人会刻意控制：反而更少小动作、更用力维持微笑 |
| C · 只看声音 | 面部可控，声音难控：停顿与语速才是真信号 |
| D · 随机权重 | 没人规定该用哪些特征、该怎么加权 |

同一份测量，四套方案给出的分数跨度通常在 20–35 个百分点，A 和 B 甚至指向相反结论——而它们**都站得住脚**。

这就是为什么报告最后落在「无法判断」，而不是某个百分比：那个数字描述的不是「他有没有说谎」，而是「作者选了哪套参数」。

每条线索在报告里都强制并列 4–5 种替代解释（`ALTERNATIVES`），因为任何一条单独成立，都足以让全部线索失去意义。

## 两端的打分逻辑是同一套

浏览器端（`js/analysis.js`）与 Python 端（`pipeline/fusion.py`）用的是同一组假设，
只是输入不同：前者读 blendshape，后者读 OpenFace 的 AU 强度。

两端都遵循一条规则：**所有方案相对同一条静息基线归一化**，
让人「坐着不动」时三套方案都落在 50% 附近，差异只来自「偏离了什么」。
否则不同权重的尺度会让某些方案天生就停在 10% 或 90%。
